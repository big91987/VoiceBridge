# 方案对比：远程桌面下怎么让本机麦克风工作

目标是同一件事：**坐在 A 电脑前，用 A 的麦克风说一句话，文字出现在远端的 B 电脑光标处。**

以下是实际试过或认真评估过的路线，以及否决原因。结论是 VoiceBridge 采用的「本机识别 + 剪贴板同步 + 远端粘贴」。

---

## 最终方案：本机识别 → 剪贴板 → UU 同步 → 远端 Paste

**链路**：本机豆包语音识别 → 写本机剪贴板 → UU 自带剪贴板同步 → 远端 Cmd+V

**为什么成立**：

- 语音识别在本机完成，延迟只有识别本身（1 秒左右），不依赖远端算力
- 传输这一步**零开发**：UU 全端自带双向剪贴板同步（Mac↔Mac，V4.18.1 起支持富文本），开关在 `操作 → 安全 → 同步剪贴板`
- 远端不需要装任何软件、不需要模型、不需要开放端口

**代价**：跨网 RTT 高（实测 400ms~1.1s，走 Tailscale DERP），必须给剪贴板同步留等待时间；剪贴板是全局的，会覆盖用户原有剪贴板内容。

## 被否决的路线

### 1. UU 远程自带麦克风上行

**思路**：直接让被控端用控制端的麦克风。

**否决**：UU Mac 被控端不支持。官方能力是「远控 Windows 时」才支持控制端麦克风，Mac 被控端没有这个选项。这是整个项目的起点问题。

### 2. Blurt（AGIHunt/blurt）

**思路**：开源的语音输入工具，自带 `blurt-remote`（手机 ↔ 电脑，Rust 实现）。

**评估过的细节**：

- 协议覆盖范围只有**手机 → 电脑**，没有 Mac 客户端、没有电脑 ↔ 电脑
- 识别是**远端本地模型**：默认 Qwen3-ASR 1.7B MLX（约 2.5GB），中文 CER 1.3%
- VAD 用本地 Silero VAD ONNX（0.6MB）
- 火山引擎 Seed-ASR 是可选云端方案，需自填 key、按量付费

**否决**：要在远端装 Blurt + 下 2.5GB 模型 + 1~2 秒识别延迟，为了打一句话装一套系统，太重。而且没有 Mac 客户端这一环，得自己写。

### 3. Jump Desktop（Fluid + Send Audio）

**思路**：Jump Desktop 支持把控制端的音频设备串流到远端。

**实际验证**：

- `Remote → Audio → Send Audio` 设备列表里只有 `None (Mute)`、两个 Unknown Device、BlackHole 2ch、LarkAudioDevice
- `Receive Audio` 子菜单只有远端本机设备（MacBook Pro、OrayVirtualAudioDevice、Jump Desktop Microphone/Audio），没有 None (Mute)
- 想走 Fluid 协议还得单独配置 entry

**否决**：要额外装一套远程软件 + 装虚拟声卡（BlackHole），为了语音输入换掉整个远程工具链，代价远超收益。

### 4. 在 Mac 上装 UU 移动版

**思路**：手机端 UU 有「原生输入框」，能调起手机输入法 + 语音，说完还能先检查再发。

**否决**：UU iOS 版 App Store 兼容性只列 iPhone / iPad / iPod / visionOS，不含 Mac，装不上。

### 5. 让远端自己跑语音输入

**思路**：在远端装语音输入法，控制端把麦克风音频转发过去。

**否决**：Mac 被控端没有麦克风上行通道（见第 1 条），音频根本过不去；用第三方音频传输又要额外一套工具。

### 6. Tailscale Exit Node

**思路**：把远端流量绕出去，避开对称 NAT 造成的 DERP 转发。

**否决**：合规与出口 IP 问题，明确放弃。

### 7. SSH 剪贴板脚本 / 网页输入框

**思路**：本机识别后，用 `ssh` 把文字发到远端执行 `pbcopy`，或在一个网页输入框里输入再同步。

**否决**：能跑通，但都是「两个以上步骤的半成品」，不符合「按住说、松手就落字」的体验目标。剪贴板同步既然 UU 已经提供，就没有理由自己维护一条 SSH 通道。

---

## 一句话总结

**识别放本机（豆包已经做得够好），传输交给 UU 的剪贴板同步（零开发），只剩「怎么把识别结果拿到手」这一个问题**——而它靠合成 Control 事件解决，代价是必须先拆掉自己的事件监听。
